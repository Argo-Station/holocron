## PLAIN SUMMARY (for Jason)

You said the sheet felt like a quilt — different tabs behaving like different apps. The census
confirms it at every layer: **the tabs save differently, compute differently, and are tested
differently.**

The headline is one class, and it is the worst kind of bug because it is silent: **on three of the
six tabs, an edit you make is thrown away when the page reloads — and the bookmark icon says
"saved" the whole time.** Buy a talent on ADVANCEMENT with a two-tap confirm; reload; the XP is
back and the talent is gone. Rename a weapon on GEAR; reload; the name is gone. Write your
character's backstory on PROFILE; reload; gone. Meanwhile the same panels' *neighbouring* controls
persist perfectly, which is why nobody caught it: the tab looks like it works.

The good news is the arithmetic underneath is sound. The shared cores — derived stats, encumbrance,
equipment resolution, dice pools — are each single and shared, with one small exception already
ruled. What is uneven is the **plumbing around them**, not the maths inside them.

## 0. WHAT THE SIX TABS ARE

`PLAYER.SHEET` renders one of six pages from a single `pages` list (see
[`Docs/NAVIGATION.md`](NAVIGATION.md) §Sheet pages for the screen IDs and anchors):

**OVERVIEW · GEAR · ABILITIES · ADVANCEMENT · VESSELS · PROFILE**

They are not six variations on one pattern. They are six independently-grown surfaces that happen
to share a tab strip — which is precisely what this census set out to establish or disprove.

## 1. SAVE / PERSISTENCE

**The store.** Roster `swrpg_saved_characters`, v1 envelope. Its code is `lib/shared/roster.js` (`window.SWRPGRoster`: the
envelope, the F-54 hold `_rosterStale`, the legacy lift, the XP repair, the tombstones, `upsertSavedCharacter`), lifted whole
and verbatim out of `player/app.jsx` so the GM writes a character through the same code (ruling
`shipyard-cargo-build-gm-seam-census` R-SCGS-1; `scripts/roster_lift_verbatim.py`, `test/roster_store.cjs`). The player keeps
its names as aliases. **`sheetData`'s schema exists NOWHERE
as a declaration** — it is implied by its readers only. That absence is the root condition under
most of §4: there is no single place that says what a character *is*, so no single place can be
wrong about it.

**Two legitimate write funnels, plus one stray:**

| funnel | what it is |
|---|---|
| `handleSheetChange` | write-through, gated by a **key-class whitelist** |
| `upsertSavedCharacter` | direct writes from creation / store / import / save; the store's and cargo's equipment write is `SWRPGRoster.writeEquipment` over it, on both hosts (R-SCGS-1) |
| `handleSelectSaved` | **the stray** — writes the roster directly |

**The write-through whitelist** admits VITALS + IDENTITY + `{commerce, speciesPick, loadout}`. It
carries **two vestigial keys nothing writes** — `conflict` and `conditions` (B-247).

**The player's improvised mark (R-SSC-5, D-229 sheet Q2 (a), ruling `f100-surfacing-sheet-concept` ADDENDUM 10 C2 (a), Q4 (a)).**
`sheet.equipment.weapons[i].improvised = true` is the one save field the sheet's surfacing lap adds. Its ONE writer is
`persistImprovised` (`player/app.jsx`, beside `persistItemState`), pressed by the "Improvised weapon" tick
(`gear-improvised-tick`) on the LOADOUT edit sheet (`LoadoutItemDetail`), through the panel's `patchEquipment` — the existing
equipment funnel, no new one. Ticked writes `improvised: true` and nothing else; unticked DELETES the key (absent = not
marked); the whole entry is marked (`qty` > 1 is not split). Never written by resolution; read only by `ItemResolve._kindFits`
(`item_kind.improvised`, §2). The tick is drawn (the engine key deleted, ADDENDUM 638). The OggDude
export has no field for it and drops it. Browser: `scripts/f100_surfacing_sheet_frames.py --built --only S4` (pressed, the
record diffed — one entry, one key — and reloaded).

**A character's own build, `own`, `looseTalents` and `changes` (F-100 M13, `f100-m13-layer` R-M13L-1..19 as amended by ADDENDUM 1; card `f100-m13-build` Lap A).** The page (`lib/modify/view.jsx`, Lap B) is its one caller, and only its address reaches it until Lap C (R-M13B-1). `SWRPGModify` (`lib/shared/charModify.js`) writes nothing but its device-local draft; `save` and `undo` RETURN one patch and the host saves it through its normal funnel.
- **`sheetData.own`:** a private user pack, `{ formatVersion: 1, packId: "own_layer", name: "own_layer", sections }`, whole records in the Homebrew validator's schema. A modified copy keeps its id as `_mode: "redefine"` with `_base` and `_from: <stamp>`; a new record is `custom_own_layer_<base36>`, `_mode: "add"`. The record under a copy changing is OFFERED and never re-applied (`SWRPGModify.offers`: `current | updated | gone`).
- **`sheetData.looseTalents`:** `{ <talentId>: { ranks, xp } }`, talents outside the trees. `SWRPGProjectionDiff`'s producers read it through `CharResolve.looseTalentIds`, and `talentsKeepingAbsentTrees` keeps them, so a later tree buy does not drop one.
- **`sheetData.changes`:** the append-only log, with before and after kept on the latest entry only. Its `stored` item carries the re-projected values and whole lists, so `undo` restores byte for byte; the page's log leaves that item out. `undo` appends the inverse and is refused unless `fingerprint(sheet)` equals the entry's `fpAfter`. The fingerprint leaves `changes` out.
- **The one Save:** `save` re-projects `talents`, `derivedBonuses` and `derivedConditional` through `SWRPGProjectionDiff.reproject` with `opts.save` (the shared step is `projectedFields`, which `packAttach` also calls), re-derives `woundBase` and `strainBase` from the resolved species with the layer included (B-1676), and RETIRES a stored `derived` (B-1677). Prices come from `CharResolve.buildPrice` (`CREATOR_PLUMBING.md`). A draft cannot hand in a stored field.
- **The draft:** `localStorage['swrpg_modify_draft']`, `{ <characterId>: { at, baseFp, patch } }`, never synced. `draftState` reports a draft whose `baseFp` no longer matches as changed since; it is never applied silently. While the page is open, `rebase` carries the draft over another device's landed copy (R-M13B-151, -152): a clash moves it to that same offer, with `baseFp` 'landed' so a reload offers it too.
- **The merge unit:** `UNITS.swrpg_saved_characters`' `xp` group in `syncMerge.js` is now the BUILD unit, so one Save never splits across a two-device conflict. `talentChoices` and `treelessTalents` joined it (R-M13B-42, amending R-M13L-11), so a talent's pick is saved with the talent. `test/sync_units_census.cjs` names each key.
- **One door (R-M13B-106):** PROFILE's Modify this Character and the species ask both open the page through `handleOpenModify`. Edit in creator and its re-entry were deleted at Lap C (R-M13B-103).
- **The page's save:** `handleModifyApply` in `player/app.jsx` saves what `save` and `undo` return. It goes around `handleSheetChange` when the patch carries names, because upsert prefers `selectedChar.species` over the sheet's. It keeps `derived: undefined`, so a retired `derived` stays retired after reload.
- **`save`'s price:** `xp` is what the change costs; `total` is what it moves on `xp.total` (a species' `starting_xp` difference, R-M13B-30, -31); `net` is `total` minus `xp`. A rank `speciesGrantApplied` accounts for prices 0 both ways (R-M13B-32). B-1696's remainder: career and specialization free ranks carry no marker, so they still refund at book.
- **The aimed form:** Homebrew's `Editor` takes one prop, `aim: { rec, onSave, onBack, intent }` (R-M13B-36). A form save calls `aim.onSave(rec, { intent })` and never writes a collection; a returned `{ ok: false, reasons }` shows in the form's own reasons. `intent` is `new` (`addOwn`) or `change` (`ownCopy`). With no `aim`, nothing changes.
- **"Modify a …" (D-460, R-M13B-56):** one list (`modifyList`) and one save path (`modifySaved`) for talents, Force powers, signature abilities, specializations and careers; a species ability's words use the species form. `aim.intent: 'change'` opens the radio on Change (R-M13B-49). Change writes this character's copy under the same id. The radio's "A new …, from" adds a record and takes the part's own Add; a signature ability only reaches the shelf, since it needs a legal tree. An own `_mode: 'add'` record opens through `/new`, because the form's route cannot find it by id. A career copy pins `careerId`, because a saved name alone would no longer find a renamed record.
- **A talent's pick on the page (R-M13B-47, -57):** `M7CharPickSheet` and `TalentSkillChoicePicker` come in as props, with no host. `charChosen` and `skillsChosen` write the sheet's own maps at the sheet's own address; an M8 skill pick goes through `pickWrite`. A refund runs `dropCellPicks`: it removes the cell's pick, Dedication's point, and a per-talent pick once the talent is no longer owned. Item picks ask on the sheet after Save, so the page's model removes their `m8Pick`. A chooser talent added from outside the trees has no address and does not ask.
- **Dedication in `charModify.js`:** a point a Dedication record accounts for (`dedicationSteps`) prices 0 both ways, carries no limit, and stays off `characteristicsAtCreation`; a record with no creation values is stamped before the raise, as `buyTalent` stamps it.
- **The sheet's head names (R-M13B-52):** `CharResolve.buildNamesOf` reads the career's and first specialization's names through the sheet's view, and `SheetSpine`'s `.sb-sub` reads through it. The saved strings are the fallback. Other readers of `sheet.career` still read the saved string.
- **Free ranks, `sheetData.freeRanks` (`f100-m13-reach-paper` §4):** `{ career: [keys], specs: { <specId>: [keys] } }`. `CharResolve.freeRanksOf` is the one reader: the record when present, else a marked reading from the skills that writes nothing. It clamps a key to its rank and drops a specialization no longer held. `normalizeCreated` writes the record at finish. `SWRPGModify` moves a rank with a moved pick (R-M13R-2); a Save touching none of skills' picks, career or specializations writes no record (`freeRecorded`).
- **Trades (§5):** `CharResolve.tradeDeltas` is the one path from a trade to numbers. The draft holds the ids and the track; `save` derives XP and credits (`tradeMove`), and `opts.creditsDelta` wins when passed (§7.2). A trade past the cap sets `pastLimit` with no `limit`: a mark in Changes and no note (R-M13R-41).
- **Game line (§6):** `book` is the field; there is no `sheet.gameLine`. `lineDraft` replaces the track, clears the trades and leaves the old track `null`, as `normalizeCreated` writes it. A Force character leaving F&D keeps Morality at its value (R-M13R-14). `book` moves `sheetForceAccess`, both PDFs and `partyStore`'s Duty tally (B-1713).
- **A loose talent's pick (§8):** on `_loose` picks, the seven with a skill or option pick ask when added. The filter on the outside-the-trees list reads the pick's kind, so an item pick stays off it (R-M13R-38, -39); a record already holding one reads and removes as today.
- **Loading (R-M13R-43):** `charModify.js` and `lib/modify/view.js` are the `modify` part of `PLAYER_PARTS`, in that order, not first load. The sheet's one read outside Modify, the pack line, is guarded on `window.SWRPGModifyView` (R-M13R-44).
- **The pack's entries:** `SWRPGModifyView.PACK_ENTRIES_LIVE` is the one switch, false until Lap C (R-M13B-24). A new item lands in the pack beside its record (R-M13B-41): the entry adds the row to `equipment` in the same patch, in the store's shape; `equipment` stays outside `SWRPGModify` and the BUILD unit, and credits do not move. The page's Undo removes a new item's row with its record (`withoutGoneRows`). `packItemRef` reads a selected row's id from its saved row, since a resolved row carries none.
Guards: `test/f100_m13_{fold,offers,loose,save,price_core,undo,merge_unit,draft,size,round_trip,species_xp,dark,free_ranks,trades,game_line,picks}.cjs`; browser `scripts/smoke_f100_m13_engine.py`, `scripts/smoke_f100_m13_reach.py`, `scripts/smoke_f100_m13_modify_part.py`, `scripts/smoke_f100_m13_line_pdf.py`, `scripts/smoke_f100_m13_page.py` (the paper smoke: Save, reload, read the record and the sheet, Undo). Bites `scripts/f100_m13_bites.py`; census `scripts/f100_m13_reader_census.py`; premises `scripts/f100_m13_premises.cjs`.

**A sync landing re-reads the OPEN sheet (B-975, ruling `f100-fix-b975-sync-overwrite-card` ADDENDUM 1).** The sheet's
`sheetData` is `PlayerApp` state, not a read of the store, so a newer copy that sync stored (`adopted` / `rechecked` /
`resolved`) used to stay unseen until the next edit wrote the old copy back over it. `PlayerApp`'s sync listener (the
one that re-reads the roster for B-971) now builds the open character's pair from the stored record with
`openedPairOf` and, when it differs, takes it and bumps `sheetLanding`, which is part of the `SheetBoundary` key: the
sheet REMOUNTS, so mount-seeded mirrors (the backstory editor, the physical-description fields) start from the newer
copy. The cost is a view reset at that moment (the open unit and folds close; the sheet reopens on WEAPONS). No prompt
is added: autosave has already stored the sheet's last edit and the merge asks where it cannot order the copies. Guard:
`scripts/smoke_b975_open_sheet_sync.py`.
**The base survives sign-out (B-1708, ruling `release-r7-bug-burndown` ADDENDUM 531, §C as amended).** `account.js`'s sign-out branch stops the watcher and leaves `swrpg_sync_base_v1`, so an edit made signed out reads as an edit at the next sign-in: both edited asks, different units merge, one side stands. The `uid` refuses it for another account, deleting the account clears it (`deleteAccount`, an edge, at `/account/`), and a full store still clears it (R-2 (b)). A base question carries `stamps`, each side's own, in memory only, and `describeConflict` reads them. **Limit, ruled out of this lap:** a first sign-in on a device's own copy, a store over `BASE_CEILING`, and a return after another account signed in here all have no base and keep the recency rule (Q2, with Jason; B-1708 stays open for them).

**A migration is not a question (B-1692, ruling `release-r7-bug-burndown` ADDENDA 484, 486).** `syncMerge.js` `mergeCanon` compares the migrated forms when the host has named a build (`SWRPGSync.setCanon`; only the player app does), at all three callers: `adopt`, `recheck`, the 409. A merge that ran before the build warmed took today's rule; `migrateStoredRoster`'s last step calls `recompare`, which reads what is stored NOW and closes a question that no longer stands (`mootOf`). **The sheet's hold:** `AccountChip` does not raise the sheet while `SWRPGSync.promptHeld()` is true (a canon named, the build cold). The merge does not wait and the chip holds the question. The hold ends once, by `recompare` (build landed or failed) or at the 30 s ceiling, and `hold_ended` is the sheet's arrival unless the player already went to it through the chip. **The backup comes first (ADDENDUM 488 R1):** each merge's `canonToWrite` and `recompare` call the canon's `backup` before any write that changes a record's form. It holds what today's rule would leave; a refusal means today's rule for that merge, and `recompare` closes nothing.
**A 409 merge lands too (B-1650, ruling `release-r7-bug-burndown` ADDENDUM 391; supersedes B-975's D1).** With the sync
base the merge goes unit by unit (`syncMerge.js` `UNITS`), so a 409 on this device's edit brings the OTHER device's
one-sided units into the record being edited. `pushNow`'s 409 branch therefore emits `adopt_written` when its merge changed
local, before the re-push, and the open sheet redraws on it like a load's landing; without it the sheet's next edit wrote
the pre-merge copy back and the push erased the other device's change. The GM's ENCOUNTERS tab re-reads the stored bench on the
same signals and on another tab's `storage` event, through `lib/shared/heldStore.js` (B-1732). **The 409's local side is the
store in the turn that merges and writes (B-1736, ruling `release-r7-bug-burndown` ADDENDUM 518),** after the tombstones answer,
falling back to what was sent on a stored null or an unparsable value; what the PUT sent is older by then, and merging it stepped
back whatever was typed while the PUT was out, which remounted this sheet on its first page. Guards:
`test/b1650_409_landing_signal.cjs`, `test/sync_seam.cjs`, `scripts/smoke_b1650_open_tab_409.py`, `scripts/b1707_loss_drive.py`
(`type409-sheet`, `typeget-sheet`).
**A load's pull lands AT its write (B-1649, ruling `release-r7-bug-burndown` ADDENDUM 387).** `adopt()` emits
`adopt_written` right after `writeLocalRespectingRoom` when the write changed a key, and the listener runs the same landing
on it, so the open sheet redraws before `adopt()`'s push loop and pack lane (measured 1.2 s earlier at fast 3G). `adopted`
keeps its time, after the pushes; its landing then finds the pair unchanged and does not remount again. Guard:
`test/b1649_adopt_redraw_at_write.cjs`.

**Another tab's write is the same moment (R-SCGS-2, ruling `shipyard-cargo-build-gm-seam-census`).** The re-adopt body is
named once, `readoptStored` (`PlayerApp`), and runs on sync's three events AND on a `storage` event for
`swrpg_saved_characters`, which every tab but the writer hears. So a GM tab's LOAD FROM, or a second player tab's store or
cargo act, reaches the open sheet before its next edit could write the old pack back. The residual, an edit typed in the
instant before the event arrives, was B-1412 (closed not reproduced, N = 24, ruling `release-r7-bug-burndown` ADDENDUM 81). Every landing then runs the roster migration (`migrateStoredRoster`, B-977, the same ADDENDUM) and, when it changed a record, `readoptStored` once more, so an open sheet takes the migrated copy before its next edit; guard `scripts/smoke_b977_adopted_legacy_migrates.py` O. Guard: `scripts/smoke_yard_cargo_acts.py` A9 (two pages, one context; bitten by
`--bite-listener`).

**Readiness (the contract, since `sheet-charbuild-correctness`).** Canonical data arrives ASYNC and
the charbuild view lands a beat AFTER the registries. Any surface rendering from either must gate on
**`useCanonicalReady`** — one module-scope hook that waits on BOTH and CALLS both idempotent loaders
itself, so it self-heals regardless of which surface mounted first. Every sheet readiness gate now
routes through it (`_canonReady` greps to zero). **A component that reads `_canonicalCharbuild`
without it repaints nothing when the data lands** — that was B-241, and it is why the hook exists
rather than a fourth inline copy. _(One older polling gate on the species-ask surface predates the
hook and is untouched; consolidating it is an open follow-up.)_
**An own-pack save or a variant toggle NULLS the discovery views under an open sheet** (`swrpg-user-packs-changed` /
`swrpg-mods-changed` → `_canonicalCharbuild`, `_canonicalRegistries`), and nothing re-loads them until the next load.
The skills VOCABULARY is pack-invariant (no `SWRPGMods.SECTIONS` entry defines skills; `test/b984_pool_skill_index_base.cjs`
pins it), so the three sheetPool.js reads of it fall back to the pristine base: `poolModSkillIndex`
(`_canonicalRegistriesBase`), `sheetSkillCharacteristic` and `yardCharPool` (`_canonicalCharbuildBase`) — B-984, ruling
`shipyard-s5-ready` P1 + ADDENDUM 3 (R-S5R-12/13); browser leg `scripts/probe_pack_change_drops_pool_dice.py` (both events + the Yard seat).

**Migrations.** Id-ref migrations write back on load (talents, powers, career, species; backed up
once). Equipment `state` is **resolve-at-render-only, permanently**. Draft and tutorial stores
migrate at read.

## 6. HOW TO KEEP THIS CURRENT

Same rule as its creator sibling. When you change sheet plumbing:

1. **A new write path** — add it to §1's funnel table, and say whether it is whitelisted.
2. **A tab's persistence changes** — update §3's row. That table is the document's centre of
   gravity; a stale ✓ there is worse than no table.
3. **A defect closes** — mark it in §5 with the commit, don't delete the row. The ledger's value is
   partly historical: B-242 is instructive *because* it shipped once.
4. **A core gains a second path** — that is a defect, not an update. File it.
